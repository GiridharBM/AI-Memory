## 1. Implemented change

The narrow D3-C correction makes the exact submitted HTTP/HTTPS URL the logical ledger identity, independent of process working directory.

Conceptually, URL ingestion changed from:

```text
URL
  ↓
Path(URL)
  ↓
Path.resolve()
  ↓
CWD-dependent ledger identity
```

to:

```text
URL
  ↓
exact submitted URL ledger identity
  ↓
CWD-independent matching
```

Historical CWD-derived rows remain stored unchanged and are recognized through narrow compatibility matching. No historical row is rewritten, merged, deleted, or migrated.

Local filesystem normalization was not changed. A filesystem `Path` follows exactly the same normalization path as before.

## 2. Exact implementation strategy

### 2.1 URL detection

Added `is_url_source()` in `app/infrastructure/state/manifest.py:27-35`.

A value is treated as a URL source only when it is a string whose parsed scheme is HTTP or HTTPS and whose parsed network location is nonempty. Local filesystem paths, empty strings, non-URL strings, and `Path` objects retain their prior handling.

Detection strips surrounding whitespace only to decide whether the value is a URL. It does not alter the stored or matched URL string.

### 2.2 Exact URL storage

Added `_normalize_ledger_source()` in `app/infrastructure/state/manifest.py:226-236`.

- URL strings are stored exactly as submitted.
- Filesystem `Path` values use the unchanged `_normalize_path()`.
- Non-URL strings are converted to `Path` exactly as before.

`add_processed_file()` and `add_failed_file()` now accept `Path | str`, but filesystem behavior is unchanged.

### 2.3 Successful URL matching

Added `contains_successful_url()` in `app/infrastructure/state/manifest.py:176-188`.

It recognizes:

1. Current exact-URL rows.
2. Recognized historical CWD-derived rows belonging to the same exact URL.
3. Only rows with a successful status.

Unsuccessful rows remain retryable under D3-B.

### 2.4 Historical-row recognition

Added `url_matches_ledger_entry()` in `app/infrastructure/state/manifest.py:43-71`.

Recognition rules:

- An exact stored URL matches itself.
- A stored exact URL never matches another URL spelling through legacy logic.
- A non-URL stored path can match an exact URL when it is the same CWD-independent `PurePath(...).as_posix()` spelling or ends with that spelling after a path separator.
- A legacy match is rejected when another stored exact URL already has the same platform-independent suffix. This prevents historical ambiguity from collapsing newly distinct URL spellings.
- Matching never rewrites the historical row.

The same helper is used for duplicate detection, failed-source grouping, source annotation, and removal matching.

### 2.5 Shared removal and annotation matching

Updated `_manifest_entry_matches()` in `app/cli/entry.py:1641-1666` to accept known exact URL paths and use the same URL matcher.

Updated its two relevant call sites:

- Source-ledger annotation.
- `pam remove` ledger matching.

Existing filename, exact-path, resolved-path, ambiguity, and canonical-source behavior for local files is unchanged.

### 2.6 Failed-source grouping

Updated `_print_failed_sources()` in `app/cli/entry.py:357-372`.

Failed rows are grouped by:

1. Their exact URL when the stored row is itself a valid URL.
2. A uniquely associated exact URL when a non-URL historical row has exactly one recognized URL counterpart.
3. Their stored spelling otherwise.

No ledger row is modified. D4 attempt counting is unchanged.

### 2.7 CLI and GUI integration

Both ingestion paths now:

1. Preserve the submitted URL string separately from `Path(source)`.
2. Call `contains_successful_url()` for URL sources.
3. Record successful, duplicate, and failed URL rows with the exact submitted URL.
4. Continue using content-hash duplicate detection for hashable files.
5. Continue using successful-path duplicate detection for non-hashable filesystem paths.

Relevant CLI code:

- `app/cli/entry.py:1096-1154`
- `app/cli/entry.py:1160-1183`
- `app/cli/entry.py:1217-1229`

Relevant GUI code:

- `app/interfaces/web/routes/interact.py:253-303`
- `app/interfaces/web/routes/interact.py:309-347`

Vector, graph, note, source-display, and GUI source identities remain exact submitted URLs. No retrieval, queue, or D4 behavior was changed.

## 3. Historical CWD-row compatibility mechanism

Compatibility is achieved through matching, not migration.

For example, a historical Windows row resembling:

```text
<old-CWD>\https:\github.com\o\r
```

is recognized for the exact submitted URL:

```text
https://github.com/o/r
```

because both reduce to the same CWD-independent `PurePath(...).as_posix()` URL-derived suffix.

The implementation:

- Preserves the old row byte-for-byte.
- Preserves its status, timestamp, filename, hash, error, and attempt history.
- Associates it with the exact URL only for matching and display grouping.
- Does not collapse an old ambiguous row into a newly distinct URL spelling when another exact URL already uses the same suffix.
- Leaves old rows intact when no unambiguous exact URL counterpart exists.

---

## 4. Why URL variants remain distinct

No parser, canonicalizer, semantic-resource extractor, redirect follower, or spelling normalizer was introduced for identity.

Consequently:

- `https://github.com/o/r`
- `https://github.com/o/r/`
- `https://github.com/o/r.git`

remain separate identities.

Likewise:

- `https://www.youtube.com/watch?v=ID`
- `https://youtu.be/ID`

remain separate identities.

Current exact URL rows are complete identities and are never subjected to legacy suffix matching against another exact URL. Vector, graph, note, display, and removal behavior for variants is unchanged.

## 5. CLI behavior

- An exact URL submitted from any working directory receives the same new ledger identity.
- A successful URL resubmitted from another directory is recognized as a duplicate.
- The workflow does not run again for the duplicate.
- A new `skipped_duplicate` attempt is recorded under existing lifecycle semantics.
- A failed URL remains retryable under D3-B.
- New failed and successful URL rows use the exact URL.
- Failed-source grouping can associate a uniquely recognized historical row with its exact URL.
- `pam remove <exact URL>` can match indexed data and recognized historical rows without depending on the current directory for URL-form derivation.
- Local filesystem ingestion and removal behavior is unchanged.

---

## 6. GUI behavior

- GUI URL form input is stripped and then treated as the same exact URL identity as the CLI.
- The GUI duplicate branch mirrors the CLI duplicate branch.
- Successful, duplicate, failed, and incomplete URL outcomes use the exact submitted URL in the ledger.
- GUI responses continue to report the submitted URL.
- Uploaded-file handling and staging behavior are unchanged.
- No frontend code was modified.

---

## 7. Remove behavior

- `pam remove <exact URL>` expands the verbatim URL and recognizes both exact and historical CWD-derived ledger forms.
- Vector and graph removal continue to use exact submitted URLs.
- Recognized historical ledger rows can be deleted without rewriting unrelated rows.
- Ambiguity protection remains in force.
- Local-file removal semantics are unchanged.
- There is still no GUI removal endpoint.

---

## 8. D4 preservation

D4 Option A remains unchanged:

- Every ingestion attempt remains a separate ledger row.
- Successful duplicates append `skipped_duplicate` rows.
- Failed retries append new rows.
- Historical rows are never merged, rewritten, migrated, or deleted by this change.
- Failed-source grouping changes only display association; it does not collapse ledger history.
- Status precedence and count semantics are unchanged.
