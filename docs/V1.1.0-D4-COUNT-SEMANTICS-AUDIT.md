# V1.1.0 D4 — Lifecycle Count Semantics Audit

**Status:** AUDIT ONLY — no implementation performed
**Date:** 2026-09-30
**HEAD:** `539c78827e8843c1ab3a317d475af1d9c6e2facd`
**Scope:** Determine whether lifecycle counts (`pam status`, system facts, API/GUI) count **ledger entries / attempts** (Option A) or **distinct logical sources / current source state** (Option B), and whether the repository already specifies a model.

---

## 1. Executive Summary

PAM exposes lifecycle counts through **three production consumers** that share **two different counting models** in the same output:

| Consumer | Ingestion counters (Processed / Skipped / Failed / Manifest entries) | Knowledge counters (Sources indexed / Indexed chunks) |
|---|---|---|
| `pam status` (CLI) | **Raw ledger entry count** (Option A) | **Distinct source count** from vector store (Option B) |
| `GET /api/system` → GUI Dashboard | **Raw ledger entry count** (Option A) | **Distinct source count** from vector store (Option B) |
| `SystemFactsService._fact_status` (QA "PAM status?") | **Raw ledger entry count** (Option A) | **Distinct source count** from vector store (Option B) |

The ingestion counters count **every ledger row** with a given status. A source that failed and was later retried successfully appears in **both** `Failed = 1` and `Successful ingests = 1` simultaneously. The knowledge counters count **distinct `source` values** in the vector store.

**The repository does not explicitly specify which model is correct.** The A5 spec attributes the counters to the "durable ledger" but is silent on entry-vs-distinct. The cumulative review (61) accepted raw-entry counting as "truthful durable counters" and marked it PASS. The untracked `docs/V1.1.0-MILESTONE-AUDIT.md` flags the consequence as a known issue (**D.4**, severity LOW-MEDIUM) and lists two possible resolutions, **neither of which was chosen**.

**Conclusion: D4 requires a product/specification decision before implementation.** No existing document, test, or specification unambiguously establishes the counting model. The current behavior is internally consistent (all three consumers agree) and is not a defect — it is an undocumented policy.

## 3. Current Counting Model

**The ingestion counters use Option A (raw ledger entry counting).** Every ledger row is counted independently. There is no grouping by source, path, hash, or any identity key. A source with N ledger entries contributes up to N to the various status counts.

**The knowledge counters use Option B (distinct source counting).** `Sources indexed` = `len({source values in vector store})`. This is already a distinct-source count.

**The two models coexist in the same output**, labeled by their source of truth:
- "Durable ledger" → raw entry counts (Option A)
- "Vector store" → distinct source count (Option B)

This is **not** Option C (hybrid) as defined in the audit request, because Option C proposes keeping attempt counts *and separately exposing* distinct current-source counts. The current output does expose both, but the "distinct" count is the vector-store index count, not a ledger-derived distinct-source count. There is no ledger-derived "distinct sources with current status X" metric.

## 4. Scenario Matrix

Notation: ledger entries listed in chronological order. "VS" = vector store. Counts are what `pam status` / `/api/system` / `system_facts` report.

| # | Scenario | Ledger entries | VS chunks | Manifest entries | Successful ingests | Skipped dupes | Failed | Sources indexed | Indexed chunks | `/api/sources` total | Per-source status |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | Source succeeds once | `[X: processed]` | 1 | 1 | 1 | 0 | 0 | 1 | 1 | 1 | `processed` |
| 2 | Source fails once, never retried | `[X: failed]` | 0 | 1 | 0 | 0 | 1 | 0 | 0 | 0 | (not listed) |
| 3 | Source fails, then succeeds on retry | `[X: failed, X: processed]` | 1 | 2 | 1 | 0 | **1** | 1 | 1 | 1 | `failed` |
| 4 | Source succeeds, then later attempt fails | `[X: processed, X: failed]` | 1 | 2 | 1 | 0 | **1** | 1 | 1 | 1 | `failed` |
| 5 | Source processed, then duplicate skipped | `[X: processed, X: skipped_duplicate]` | 1 | 2 | 1 | 1 | 0 | 1 | 1 | 1 | `processed` |
| 6 | Non-hashable source fails, then succeeds (D3-B retry) | `[X: failed, X: processed]` | 1 | 2 | 1 | 0 | **1** | 1 | 1 | 1 | `failed` |

**Key observations:**

- **Scenarios 3, 4, and 6 are indistinguishable in the counts.** All three produce `Failed = 1` and `Successful ingests = 1` for the same source. The source is indexed (1 chunk, appears in `/api/sources`) yet `Failed = 1`.
- **Scenario 6 was impossible before D3-B.** A failed non-hashable source would have been blocked by `contains_path` on retry, producing only `[X: failed]` (scenario 2 counts). D3-B made the retry proceed, creating the two-entry ledger that scenarios 3/4/6 share.
- **Scenario 5** is the only multi-entry scenario where `Failed = 0`. The `skipped_duplicate` count is 1 and `Successful ingests` is 1 — both accurate as entry counts.
- **`/api/sources` total** counts distinct vector-store sources (1 in all scenarios except 2), independent of ledger entry count.
- **Per-source status** in `/api/sources` uses the precedence model: scenario 3/4/6 show `failed` (failed-wins), scenario 5 shows `processed`.

## 5. `pam status` Behavior

`pam status` reports **raw ledger entry counts** for all ingestion metrics:

| Row | Value | Model |
|---|---|---|
| Manifest entries | `len(ledger)` | Option A (entries) |
| Successful ingests | `sum(status == "processed")` | Option A (entries) |
| Skipped duplicates | `sum(status == "skipped_duplicate")` | Option A (entries) |
| Failed | `sum(status == "failed")` | Option A (entries) |
| Sources indexed | `len({source in VS})` | Option B (distinct) |
| Indexed chunks | `len(VS entries)` | raw VS entries |

A source that failed then succeeded (scenario 3) shows `Manifest entries = 2`, `Successful ingests = 1`, `Failed = 1`, `Sources indexed = 1`. The `Failed = 1` is accurate as an entry count but may mislead a user into thinking the source is currently broken.

## 6. `system_facts.py` Behavior

`SystemFactsService._fact_status` produces a natural-language sentence mixing both models:

> "PAM is running (vX). Indexed {src} sources / {chk} chunks. And {processed} successful ingests, {skipped} skipped, {failed} failed."

- `{src}` / `{chk}` → vector store (distinct sources / raw chunks) — Option B for sources
- `{processed}` / `{skipped}` / `{failed}` → raw ledger entry counts — Option A

The QA user asking "What is the PAM status?" gets `Failed = 1` for a source that is actually indexed and working (scenario 3). This is the same behavior as `pam status`, expressed in prose.

## 9. Conflict / Ambiguity Analysis

**The ambiguity is real and has three facets:**

1. **Entry vs distinct-source for ingestion counters.** A source with `[failed, processed]` contributes to both `Failed` and `Successful ingests`. Under Option A this is correct (2 entries, 2 counts). Under Option B it is double-counting (1 source, should be in exactly one bucket).

2. **Precedence vs counting model interaction.** The documented precedence (`failed > processed > skipped_duplicate > indexed`) is a **per-source-row** concept (one status per source). The counting metrics are **per-entry** concepts (each entry counted). These are different axes. The precedence determines the *label* on a source row; the counting model determines the *tally*. A source can be labeled `failed` (precedence) while also contributing to `Successful ingests` (entry count). This is not a contradiction, but it is confusing.

3. **Vector-store vs ledger as source of truth for "sources."** `Sources indexed` comes from the vector store (distinct). `Successful ingests` comes from the ledger (entries). A source can be indexed (in VS) with `Failed = 1` (in ledger). The two counters answer different questions ("how many sources are in the index?" vs "how many ingest attempts succeeded?") but are displayed in the same table without disambiguation.

**The untracked milestone audit (D.4) already identified facet 1** and proposed two resolutions:
- (a) newest ledger entry wins per source (would change both the per-row status AND the counts), or
- (b) document the conservative choice as intended.

Neither was adopted. The current code implements neither — it keeps `failed`-wins for the per-row status and raw-entry counts for the metrics.

## 10. Options A / B / C

### Option A — Attempt / Ledger Counting (current behavior for ingestion counters)

Counts = number of ledger rows with each status.

| Scenario | Failed | Successful ingests |
|---|---|---|
| 3: fail → succeed | 1 | 1 |
| 4: succeed → fail | 1 | 1 |

**Advantages:**
- Simple, stateless, no identity resolution needed.
- Truthful as a record of what happened (every attempt is counted).
- Consistent with append-only ledger (no supersession needed).
- Already implemented and tested.

**Disadvantages:**
- A retried-then-succeeded source shows `Failed = 1` forever, even though it is indexed and working.
- `Manifest entries` can exceed `Sources indexed` with no explanation.
- A user cannot tell from `pam status` alone whether `Failed = 1` means "1 source is currently broken" or "1 attempt failed in the past."

### Option B — Distinct Current-Source Counting

Each logical source appears in exactly one current-status bucket, using the documented precedence.

| Scenario | Failed | Successful ingests |
|---|---|---|
| 3: fail → succeed | 0 | 1 |
| 4: succeed → fail | 1 | 0 |

**Advantages:**
- Answers "how many sources are currently in each state?" — more actionable.
- `Failed` would mean "currently broken," not "ever failed."
- Consistent with the per-source status shown in `/api/sources`.

**Disadvantages:**
- Requires resolving source identity across ledger entries (path, hash, URL forms). The existing `_source_forms` / `_manifest_entry_matches` machinery does this for the per-row status but is not used for counts.
- A source that failed then succeeded would show `Failed = 0`, losing the historical fact that a failure occurred. The failure is still in the ledger but not surfaced in the count.
- Changes the meaning of `Manifest entries` (would need to become "distinct sources" or be renamed).
- More complex; needs a grouping key that handles the D3-C path-mangling issue (a URL's ledger identity is a mangled path, so grouping by `original_path` may not match the vector store's `source` value).

### Option C — Hybrid

Keep attempt counts AND separately expose distinct current-source counts.

**Advantages:**
- Preserves historical attempt data while adding a current-state view.
- Could coexist with the current output by adding rows (e.g., "Sources currently failed: N" alongside "Failed attempts: N").

**Disadvantages:**
- Introduces a second counting model to maintain and explain.
- The current output already mixes two models (ledger entries + vector-store distinct) without labeling them as different *kinds* of counts. Adding a third would increase confusion.
- The "distinct current-source count" would need the same identity-resolution machinery as Option B, with the same D3-C complications.
- Likely unnecessary scope: the per-source status in `/api/sources` already provides the current-state view at the individual source level.

## 11. Compatibility Implications

| Consumer | Impact of switching to Option B |
|---|---|
| `pam status` | `Failed` / `Successful ingests` / `Skipped duplicates` / `Manifest entries` values would change for any source with multiple entries. Tests in `test_cli_status.py` assert label presence, not values, so they would still pass. |
| `GET /api/system` | `metrics.failed` / `processed` / `skipped_duplicates` / `ledger_entries` would change. GUI `Dashboard.tsx` displays these verbatim — no code change needed, but displayed values change. |
| `system_facts._fact_status` | The natural-language sentence would change. No test asserts the value (only the intent routing). |
| `/api/sources` | Unaffected (already distinct-source). |
| `pam sources --failed` | Unaffected (D3-A, ledger-driven, already groups by `original_path` for display). |

**No consumer would break** (no test asserts specific count values for multi-entry sources), but the *meaning* of the numbers would change, which is a user-visible behavior change requiring a version note or changelog entry.

- `test_cli_status.py::test_reports_processed_failed_and_skipped` seeds 4 entries for **4 distinct sources** (a.md, b.md, c.md, d.md) — it does not test a source with multiple entries. It asserts label presence, not values.

**A D4 decision would require new tests** for:
- A source with `[failed, processed]` → what should `Failed` / `Successful ingests` be?
- A source with `[processed, failed]` → what should `Failed` / `Successful ingests` be?
- A source with `[processed, skipped_duplicate]` → already covered by scenario 5 behavior.
- Consistency across `pam status`, `/api/system`, and `system_facts` for the same multi-entry ledger.

## 13. Recommendation

**A product/specification decision is required.** No existing document, test, or specification unambiguously establishes the counting model. The current behavior (Option A for ingestion counters, Option B for knowledge counters) is internally consistent and not a defect, but the choice is undocumented and has user-visible consequences (a retried-then-succeeded source shows `Failed = 1` forever).

The untracked `docs/V1.1.0-MILESTONE-AUDIT.md` (D.4) already flagged this and proposed two resolutions:
1. Make the newest ledger entry win per source (changes both per-row status and counts), or
2. Document the conservative choice as intended.

**Recommended next step:** a spec decision on whether `Failed` / `Successful ingests` / `Skipped duplicates` should mean "number of attempts" (Option A) or "number of sources currently in that state" (Option B). This decision should be recorded in the A5 or A3 phase documentation before any D4 implementation. Do not implement until the decision is made.

## 17. Decision / Resolution

- D4 decision: **Option A — recorded ingestion attempts**.
- Decision status: **CLOSED**.
- Lifecycle ingestion counters are attempt-based: they count ledger entries by status, not logical sources in their current state.
- A source with separate `failed` and `processed` attempts therefore contributes to both `Failed` and `Successful ingests`; this is intentional.
- The retained failed count means “one recorded ingestion attempt failed,” not “one source is currently broken.”
- The locked per-source precedence—`failed > processed > skipped_duplicate > indexed`—is unchanged.
- **No implementation change was required:** the existing ledger, CLI, API, system-facts, and GUI behavior already matches Option A.
- **No application, test, configuration, or retrieval code was modified for D4.**
- D3-C remains deferred; D5 remains unchanged.
- Consistency note: `docs/phases/44_PHASE_6G_APPLICATION_PRODUCTION_READINESS_DISCOVERY.md:94` already characterized ledger counts as attempts rather than unique sources; D4 approves that as the formal lifecycle-count policy.
