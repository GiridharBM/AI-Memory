## 1. Executive verdict

**BLOCKED — FIX REQUIRED**

Three defects are reachable, reproducible on ordinary inputs, and violate locked D3-C requirements. The core identity fix (requirement 1, 5, 9) is correct and genuinely narrow, and requirements 4, 8, 10 and the frozen-file rules hold. However:

| ID | Severity | Defect | Violated requirement |
|----|----------|--------|----------------------|
| **B1** | **Blocker** | `pam remove <URL>` can no longer delete exact-URL ledger rows, so a removed URL can never be re-ingested (ledger says indexed, vectors are gone). Confirmed as a **regression** versus `457f6de^`. | 1, 5, 7 |
| **B2** | **Blocker** | The legacy suffix matcher strips trailing slashes, so `https://github.com/o/r` and `https://github.com/o/r/` are not distinct when only historical rows exist. Removing one spelling deletes the other spelling's ledger row and orphans its vectors. | 2, 3, 7, 9 |
| **B3** | **Blocker** | Two unrelated entries match the URL: (a) a historical row created from a *different* URL that itself embeds a scheme (`https://x/a/https://github.com/o/r`), and (b) a **local file** whose real path is `C:\proj\https:\github.com\o\r`. | 6 (invariant "no unrelated match"), 15 |

The stated audit invariant — *"Can an unrelated historical ledger entry match this URL? Expected answer: NO"* — is **violated** for case (a) and case (b).

Root cause shared by all three: D3-C made the ledger **write** path URL-aware (`_normalize_ledger_source`) but left the **read/delete** paths (`remove_entry`, `_normalize_path`, `remove_source` deletion loop) CWD-path-only, and the historical-compatibility matcher is a suffix heuristic rather than an exact historical-form comparison.

Push must not proceed until B1–B3 are fixed and covered by tests.

## 3. PurePath suffix matcher analysis

`_url_ledger_suffix("https://github.com/o/r")` → `"https:/github.com/o/r"` **[E]** — pathlib collapses the `//` after the scheme, exactly reproducing the historical mangling. Required marker: the entry must end with `"/" + "https:/…"`, i.e. the URL tail must be preceded by a directory separator.

Property table (all **[E]**):

| Entry row | Matches `https://github.com/o/r`? | Comment |
|---|---|---|
| `C:\oldcwd\https:\github.com\o\r` | **True** | intended historical row (A) |
| `D:\anothercwd\https:\github.com\o\r` | **True** | intended historical row (B) |
| `https:\github.com\o\r` (project-relative) | **True** | intended historical row (C) |
| `/home/dev/proj/https:/github.com/o/r` (POSIX abs) | **True** | cross-platform historical row |
| `C:\oldcwd\https:\github.com\o\other` | False | correct |
| `C:\proj\notes\a.md` | False | correct |
| `C:\proj\https:\github.com\o\r` (a **local file** at that path) | **True** | **B3(b) violation** |
| `D:\…\https:\x\a\https:\github.com\o\r` (row of URL `https://x/a/https://github.com/o/r`) | **True** | **B3(a) violation** |

Answers to the specific questions:

- **How is the suffix extracted?** `PurePath(url).as_posix()` — platform-dependent flavour (`PureWindowsPath` on Windows, `PurePosixPath` on POSIX), but empirically identical output for URLs on both.
- **Delimiters required?** A `/` immediately before `https:/`. The equality branch covers the project-relative form `https:\github.com\o\r`.
- **Do arbitrary filesystem paths accidentally match?** Only files that literally live under a directory named `https:` — possible but pathological. **Yes, they match** (B3(b)).
- **Can two different URLs produce the same suffix?** **Yes**: any trailing-slash pair. `https://github.com/o/r` and `https://github.com/o/r/` both → `https:/github.com/o/r`; likewise `https://youtu.be/ABC` and `https://youtu.be/ABC/`. `pathlib` drops the trailing slash. Every other tested pair (`.git`, `youtu.be`, `?v=`, `&t=`, `&list=`, host case, `:443`, fragment, `%2F`) yields a distinct suffix **[E]**.
- **Can a local path be interpreted as a URL?** `is_url_source` is `False` for every `Path` object (type-guarded) and for Windows paths (`C:` is not `http`/`https`), and `False` for mangled `https:\github.com\o\r` (empty netloc). `Path` inputs never take the URL branch.
- **Windows vs POSIX?** Legacy POSIX rows match when the separator is `/`. A *Windows* legacy row read on POSIX (`…\https:\github.com\o\r`) is **not** normalized because `entry_path.replace(os.sep, "/")` uses the **running** platform's separator **[D]**. A ledger copied between platforms keeps its Windows backslashes and stops matching on POSIX.
- **Drive letters?** `C:` is never parsed as a URL scheme, so drive prefixes cannot be mistaken for URL identity; they do not appear in the suffix comparison.
- **Project-relative rows?** Handled by the equality branch; verified True.
- **Slash/backslash inside URL paths?** A URL containing a backslash, e.g. `https://h/a\b`, yields suffix `https:/h/a\b` (Windows flavour) and would not match its own POSIX-normalized legacy row. Edge case, no practical ingestion path.
- **Malicious/unusual URL colliding with a historical local-file path?** Yes — B3(b) above.

**`known_exact_paths` guard side effects:** the guard fires whenever *any* exact URL row shares the suffix. Because suffixes collapse trailing slashes, adding one exact row for `…/o/r` **disables** legacy matching for `…/o/r/` too. It also makes behaviour order-dependent: legacy recognition works until the first exact row is written, then silently stops.

## 4. Collision analysis

Constructed and executed collisions:

1. **Trailing-slash collapse (B2).** Only a historical row exists, produced from `https://github.com/o/r/` (stored `C:\oldcwd\https:\github.com\o\r`). Both `https://github.com/o/r` and `https://github.com/o/r/` return `True` **[E]** → the base spelling is falsely reported as a duplicate and is never ingested.
2. **Nested-scheme cross-URL collision (B3a).** URL `https://x/a/https://github.com/o/r` has historical row `…/https:/x/a/https:/github.com/o/r`. Because `endswith("/" + "https:/github.com/o/r")` is satisfied by the **tail** of that row, it matches the unrelated `https://github.com/o/r` **[E]**.
3. **Local-file collision (B3b).** A real file at `C:\proj\https:\github.com\o\r` matches the URL **[E]**; it would be annotated as the URL's ledger row, suppressed as a duplicate of it, and deleted by `pam remove <URL>`.
4. **Suffix-extension non-collision (correct).** `…/o/r/tree/main` and `…/o/rx` do not match `…/o/r` **[E]**.
5. **Exact-row non-collision (correct).** Exact rows compare byte-wise only: base vs slashed and slashed vs base are both `False` **[E]**.
6. **Credential-bearing URL.** `https://user:pw@host/x` stores credentials verbatim in the ledger and they are echoed by `pam sources --failed`. This is **pre-existing** (the mangled row also contained them verbatim), so D3-C neither introduces nor worsens it; the ledger is a local file.

Net: **unrelated-entry matches are possible** (cases 1–3) → audit invariant not met.

- Rows A–E for the **exact same URL** match. Correct.

## 8. Remove safety analysis

Executed against the committed tree (helper `_seed_url` from the repo's own test suite used for realistic seeding) **[E]**:

| Scenario | Result |
|---|---|
| **B1:** fresh exact-URL row (the format D3-C now writes), removed from the same CWD | exit 0, `Ledger entries removed 0`, **row survives**; vectors deleted; `contains_successful_url` still `True` |
| **B1 end-to-end:** ingest → remove → re-ingest | STEP 2 removes 0 ledger rows, STEP 3 prints **"Ingest skipped (duplicate)"** — source is permanently un-re-ingestable while unindexed |
| **B2:** ledger row + vectors keyed by `https://github.com/o/r/`, then `pam remove https://github.com/o/r` | exit 0, `Vector chunks removed 0`, `Ledger entries removed 1` → **the other spelling's row is deleted and its 2 vector chunks are orphaned** |
| Two variants + `…/o/rx` present, remove `…/o/r` | no cross-match; nothing removed (masked by B1) |
| Historical rows only, remove from unrelated CWD | works (covered by the new test) |
| Local file removal | unchanged (existing suite passes) |

**B1 root cause [D + E]:** `ManifestManager.remove_entry()` (`manifest.py:195-214`) matches rows through `_normalize_path()`, which resolves the stored value. `remove_source` (`entry.py:618-624`) converts `entry.original_path` back to a `Path` and re-resolves it. For a row stored as the exact URL `https://github.com/o/r`, that resolution yields `https:\github.com\o\r`, which never equals the stored string. `Ledger entries removed 0` is printed and the command still exits 0, so the failure is silent.

**B1 is a regression, proved by execution [E]:**

| Step | `457f6de^` | `457f6de` |
|---|---|---|
| ingest URL → ledger row | `('processed', 'https:\\github.com\\o\\r')` | `('processed', 'https://github.com/o/r')` |
| `pam remove <URL>` → ledger removed | **1**, ledger `[]` | **0**, row survives |
| re-ingest | workflow runs (re-ingested) | **skipped_duplicate** |

Secondary impact: `pam status` counts ledger `processed` rows (`entry.py:170`), so the surviving row keeps a removed source counted as processed.

`ManifestManager.remove_entry` is the single narrow place that must learn the URL spelling; the caller-side `Path()` round-trip is the second half of the same bug.

## 9. Failed-source grouping analysis

`_print_failed_sources` remains ledger-driven and read-only (no ledger write, no quarantine, no create) — requirement preserved. The added grouping is **display-only** and does not touch ledger rows **[E]**.

Per-use necessity:

| Use | Needed for D3-C? | Assessment |
|---|---|---|
| duplicate detection (`contains_successful_url`) | **Yes** | core fix |
| CLI/GUI success + failure row identity | **Yes** | core fix |
| failed-source grouping | **No** (cosmetic) | **unnecessary and ineffective** — see below |
| source annotation (`pam sources`) | **No** (cosmetic) | **unnecessary** |
| removal matcher | **Yes** (parity with pre-commit CWD-dependent behaviour) | correct intent, blocked by B1/B2 |

Grouping effectiveness is order-dependent and self-defeating **[E]**: `exact_urls` is a list that may contain duplicates, and the guard in `url_matches_ledger_entry` makes any historical row return `False` as soon as an exact row with the same suffix exists. With ledger = {1 historical failed row, 2 exact failed rows}, the historical row computes `matches=0` and is **not** regrouped; with 2 exact rows the `len(matches) == 1` test could never be satisfied either. So the stated goal ("historical rows can be associated with their exact URL for display") holds only while at most one exact row exists — precisely the transient state — and silently stops afterwards.

Classification: **D/E — unnecessary behaviour change with an unreliable effect.** Recommended: drop the grouping, or (if kept) dedupe `exact_urls` and drop the guard.

## 18. Defects found

### B1 — `pam remove` cannot delete exact-URL ledger rows (Blocker)
- **Where:** `app/cli/entry.py:618-624` (deletion loop) and `app/infrastructure/state/manifest.py:195-214` (`ManifestManager.remove_entry`).
- **What:** rows stored with the exact URL are re-resolved through `_normalize_path`, become the mangled CWD form, and never match. `Ledger entries removed 0` is printed and the command exits 0.
- **Impact:** after `pam remove <URL>` the vectors/KG are gone but the ledger still claims the source is indexed, `pam status` over-counts it, and `pam ingest <URL>` answers `skipped_duplicate` forever. Silent data unavailability; D3-C's own new row format is what triggers it.
- **Proof:** [E] same-CWD and cross-CWD ingest→remove→re-ingest on the committed tree vs the parent tree (§8).

### B2 — trailing-slash variants are not distinct through the legacy matcher (Blocker)
- **Where:** `app/infrastructure/state/manifest.py:38-40` (`_url_ledger_suffix` uses `PurePath`, which strips trailing slashes).
- **What:** `https://github.com/o/r` and `https://github.com/o/r/` share a suffix; with only historical rows present both match both.
- **Impact:** false `skipped_duplicate` (requirement 2), and `pam remove` of one spelling deletes the other spelling's ledger row while orphaning its vectors (requirements 7, 9) **[E]**.

### B3 — unrelated entries match the URL (Blocker)
- **Where:** `app/infrastructure/state/manifest.py:70-71` (`endswith("/" + suffix)` with no anchor on the first scheme marker; no filesystem disambiguation).
- **What / impact:**
  - (a) historical row of URL `https://x/a/https://github.com/o/r` matches `https://github.com/o/r` **[E]**;
  - (b) a real local file at `C:\proj\https:\github.com\o\r` matches, is annotated as the URL's row, is suppressed as a duplicate of it, and would be deleted by `pam remove <URL>` **[E]**.

### B4 — historical compatibility silently switches off once an exact row exists (Major)
- **Where:** `manifest.py:65-69` (`known_exact_paths` guard), consumed by `_print_failed_sources`, `_annotate_source_ledger`, `remove_source`, `contains_successful_url`.
- **What:** with any exact row sharing the suffix, legacy matching returns `False` everywhere. Failed-source grouping computes `matches=0` **[E]**; historical rows stop being removable/annotatable; behaviour differs depending on whether an exact row happens to exist.
- **Impact:** contradicts requirement 6 ("historical rows remain compatible") and makes the grouping/annotation changes ineffective.

### B5 — `pam sources --failed` grouping is unnecessary and unproven (Minor)
- **Where:** `entry.py:357-372`.
- **What:** display-only behaviour not required by D3-C; its only test assertion (`count(url) == 1`) cannot distinguish "grouped" from "exact row printed alone" (§9, §14 #7).

### B6 — whitespace asymmetry between ledger and ingestion identity (Minor)
- **Where:** `manifest.py:27-35` vs `manifest.py:234-235`.
- **What:** `is_url_source` strips for detection, but the ledger stores the padded string; `DocumentIngestionService._normalize_source` (`service.py:302-310`) strips, so vectors/notes/graph use the stripped URL. `  https://…  ` and `https://…` therefore are two ledger identities for one indexed source, and the stripped resubmission is not detected as a duplicate **[E]**.

### B7 — efficiency/clarity nits (Minor)
- `exact_url_paths` is rebuilt inside the per-row loop in `_annotate_source_ledger` (`entry.py:453-455`); the guard iterates all exact rows per (entry × target), making `remove`/annotation O(n·m).
- `_print_failed_sources` builds `exact_urls` with duplicates, making `len(matches) == 1` fragile.
- `url_matches_ledger_entry`'s `known_exact_paths: Collection[str] | None = None` is fine, but callers pass untyped lists of `Any`-ish values from ledger dicts.
