# V1.1.0 D3-C — URL Identity Specification Audit

**Status:** AUDIT ONLY — no implementation performed.
**Date:** 2026-10-01.
**HEAD:** `b7f8ae236dffc9743083cb0c42d03c7890dd0927`.
**Scope:** Determine what should constitute the identity of a remote URL source before any D3-C URL implementation is considered. Broad filesystem normalization is out of scope.

---

## 1. Executive summary

PAM has a split URL-identity model:

- **Operational, indexed, displayed, and removed vector/graph identity:** exact submitted URL string.
- **Ledger duplicate/matching identity:** CWD-dependent `Path`-mangled representation.
- **Ledger display grouping:** exact stored `original_path`.
- **Ingestor resource selection:** semantic owner/repository or video identifiers that are discarded for storage and duplicate purposes.

The narrow demonstrated defect is not that PAM preserves verbatim URLs. Verbatim preservation is explicitly specified and architecturally consistent for vectors, graphs, notes, listings, and removal. The defect is that **ledger duplicate detection converts a URL into a filesystem `Path` and resolves it against the process working directory**, so the same verbatim URL can acquire different historical ledger identities from different directories.

The repository does not specify a complete canonical-URL policy. It does establish that:

1. The same verbatim URL submitted from different working directories should have the same logical identity.
2. Existing URL variants are stored as separate vector sources.
3. Ingestor-level resource equivalence has not been adopted as stored-source equivalence.

Therefore, the evidence supports a narrow conclusion for exact duplicate URLs across directories, but **a complete URL-equivalence policy still requires a specification decision**.

No source, test, configuration, frontend, retrieval, queue, documentation, or prior-audit file was modified. No commit, staging, or push was performed except for creating this audit report.

## 2. Current URL architecture

### 2.1 Ingestion input and duplicate checking

A CLI GitHub or YouTube command passes the submitted URL unchanged as a string:

- `app/cli/entry.py:85-86`
- `app/cli/entry.py:134-145`

A GUI URL is stripped of surrounding whitespace and then passed unchanged as a string:

- `app/interfaces/web/routes/interact.py:185`
- `app/interfaces/web/routes/interact.py:193`

Both `_run_ingest` implementations then execute the same identity sequence:

1. Convert the submitted string with `ledger_path = Path(source)`.
2. Assign `digest = None` because the source is not a `Path`.
3. Call `manifest.contains_successful_path(ledger_path)`.
4. If no successful path identity is found, run the ingestion workflow.
5. Append a `processed`, `failed`, or `skipped_duplicate` ledger row.
6. Never rewrite an earlier ledger row.

## 4. Ingestor semantic identity

### 4.1 GitHub

Acceptance requires:

- HTTP or HTTPS scheme.
- Host exactly `github.com` after lowercasing.
- At least two nonempty URL path segments.

Relevant code:

- `app/infrastructure/ingestion/github_readme_ingestor.py:25-35`

Resource selection uses only the first two path segments:

- Owner: first segment.
- Repository: second segment, with a trailing `.git` removed.

Relevant code:

- `app/infrastructure/ingestion/github_readme_ingestor.py:81-100`

Consequences:

- Trailing slashes do not affect repository-coordinate extraction.
- A `.git` suffix does not affect repository-coordinate extraction.
- Additional path segments, branch or ref paths, queries, and fragments do not affect repository-coordinate extraction.
- Owner and repository strings are preserved in their submitted case for API requests and metadata.
- The fetched resource is the repository’s README response, not necessarily the branch, path, or revision implied by the submitted URL.
- The stored `SourceDocument.source` nevertheless preserves the complete submitted URL.

The ingestor therefore collapses several spellings for remote fetching while PAM retains them as separate stored identities.

### 4.2 YouTube

Acceptance requires an HTTP or HTTPS URL on one of:

- `youtube.com`
- `www.youtube.com`
- `m.youtube.com`
- `youtu.be`
- `www.youtu.be`

after lowercasing the host.

Relevant code:

- `app/infrastructure/ingestion/youtube_transcript_ingestor.py:33-38`

Resource selection extracts a video identifier from:

- The first path segment of a `youtu.be` URL.
- The `v` query parameter of a `/watch` URL.
- The second path segment of an `embed`, `shorts`, `live`, or `v` URL.

Relevant code:

- `app/infrastructure/ingestion/youtube_transcript_ingestor.py:87-106`

Consequences:

- Timestamp, playlist, and other extra query parameters do not affect current video-ID extraction for supported forms.
- Fragments do not affect current extraction for supported forms.
- `shorts`, `live`, `embed`, and canonical `watch` URLs containing the same video ID retrieve the same transcript resource but produce different stored sources.
- Unsupported forms, including channel or malformed URLs, cannot be treated as the same video merely because they appear related.
- The transcript response may supply a resolved video ID, but the stored `SourceDocument.source` remains the submitted URL.

### 4.3 Generic URL ingestion

`DocumentIngestionService` recognizes HTTP/HTTPS URLs but contains no generic URL canonicalizer. Remote ingestion is limited to the registered GitHub and YouTube adapters through normal ingestor selection.

Relevant code:

- `app/infrastructure/ingestion/service.py:146-176`
- `app/infrastructure/ingestion/service.py:279-311`

## 5. Current duplicate logic

### 5.1 Comparison points

- `_normalize_path`: converts a supplied path into the ledger’s stored spelling.
- `contains_path`: tests for any prior row with that spelling.
- `contains_successful_path`: tests for a prior successful row with that spelling.
- `contains_successful_hash`: tests for a prior successful digest; URLs never reach this branch.
- `_source_forms`: expands removal/listing targets, including both verbatim and derived URL spellings.
- `_canonical_source`: anchors non-absolute values to the configured project root.
- `_manifest_entry_matches`: compares stored ledger fields against expanded targets.

Only `_normalize_path`, `contains_path`, `contains_successful_path`, and `remove_entry` participate directly in ledger duplicate/delete comparisons. `_source_forms`, `_canonical_source`, and `_manifest_entry_matches` participate in removal and row annotation, not duplicate ingestion.

Relevant code:

- `app/infrastructure/state/manifest.py:93-125`
- `app/infrastructure/state/manifest.py:132-150`
- `app/infrastructure/state/manifest.py:231-239`
- `app/cli/entry.py:1537-1613`

### 5.2 Call chains

#### A. First successful URL ingestion

1. Submit exact URL `U`.
2. `digest` is `None`.
3. Normalize `Path(U)` under the current CWD, producing ledger spelling `L(A)`.
4. No successful `L(A)` row exists.
5. Ingest and fetch the remote resource.
6. Store or replace vector and graph data under exact `U`.
7. Append a `processed` ledger row with spelling `L(A)`.
8. The failed-source listing does not include the new row.
9. Removal can use exact `U`, provided the ledger form was created under the same CWD or is otherwise matched.

#### B. Same URL from the same CWD

1. Submit exact `U`.
2. Normalize `Path(U)` to the same spelling `L(A)`.
3. Find the successful row.
4. Record a new `skipped_duplicate` ledger row.
5. Do not run the workflow.
6. Do not replace vectors, graphs, or notes.
7. Report the source as already recorded.
8. Removal can address both the vector source and historical ledger row.

#### C. Same URL from a different CWD

1. Submit exact `U`.
2. Normalize `Path(U)` to a different spelling `L(B)`.
3. Fail to find the earlier successful `L(A)` row.
4. Run the workflow again.
5. Replace vector and graph data owned by exact `U`.
6. Append another `processed` row with spelling `L(B)`.
7. Historical attempt counts increase.
8. Removal through exact `U` normally reaches the indexed data but may miss the older CWD-derived ledger row.

#### D. URL variant from the same CWD

1. Submit a different spelling `V`.
2. Vector identity is `V`, not `U`.
3. Ledger normalization produces a different spelling.
4. No duplicate is found merely because `U` and `V` resolve to the same remote resource.
5. Ingest and store `V` as a separate vector identity.
6. Preserve previously stored `U` data.
7. Append a separate ledger row.
8. Failed-source grouping treats the variants separately.
9. Removal of `V` does not remove `U`; a bare shared filename may instead trigger ambiguity protection.

#### E. URL variant from a different CWD

The outcome combines D with C:

- Separate vector identity because the submitted string differs.
- Separate ledger spelling because both URL spelling and CWD influence the normalized form.
- No reliable duplicate, retry-association, failed-source grouping, or failed-only removal behavior across the old and new rows.

D3-B ensures that a failed URL remains retryable, but it does not supply the missing canonical identity needed to recognize the retry as the same historical source after a duplicate has succeeded.

## 6. Cross-CWD behavior

| Case | Identity outcome |
|---|---|
| Same verbatim URL, successful first ingestion | Vector and indexed identity stable; historical ledger identity depends on CWD |
| Same verbatim URL resubmitted from original CWD | Correct `skipped_duplicate`; no repeated workflow |
| Same verbatim URL resubmitted from another CWD | Possible repeated workflow and another successful ledger row |
| Same failed URL retried from another CWD | Retry still proceeds under D3-B, but the new failure is not reliably associated with the old failure |
| Failed-only URL removed from another CWD | Verbatim vector data is absent; historical CWD-derived ledger row may not match, producing “Source not found” |
| Successful URL removed from another CWD | Verbatim vector/graph data can be removed; old ledger row may remain unmatched |
| CLI versus GUI URL submissions | Same URL duplicate logic, but each still uses the process CWD for ledger normalization |

Thus, exact-string preservation does not by itself provide CWD independence. The ledger conversion is the inconsistent layer.

## 7. URL equivalence analysis

PAM currently has no URL-equivalence relation. Vector identity, GUI source identifiers, failed-source grouping, and display use exact-string equality. Ingestor acceptance may ignore parts of a URL that storage nevertheless preserves.

| URL variation | Current PAM treatment | Ingestor-level resource relationship |
|---|---|---|
| Exact same spelling | Same vector identity; ledger identity stable only within the same CWD | Same submitted resource identity |
| Same spelling from another CWD | Same vector identity; different ledger spelling | Same submitted resource identity |
| Trailing slash | Different vector identity | Same GitHub repository coordinate; same YouTube video extraction for supported short forms |
| Host casing | Different vector identity; GitHub and YouTube acceptance lowercases the host for matching | Same host class for acceptance, but path/resource casing is preserved |
| Default port | Different vector identity; host comparison does not remove an explicit default port | Cannot be equated by current code |
| Fragment | Different vector identity | Ignored by current GitHub coordinate and supported YouTube extraction, but retained for storage and navigation meaning |
| Query string | Different vector identity | Ignored except for YouTube’s `v` parameter and any parameters expressly used by extraction |
| Percent encoding | Different vector identity | `urlparse` does not decode or normalize the value; equivalence cannot be established from current code |
| Dot segments or path normalization | Different vector identity | Filesystem-style `Path` normalization is not URL-path normalization and remains CWD-anchored |
| GitHub `.git` suffix | Different vector identity | Same repository coordinate after stripping `.git` |
| GitHub branch, ref, or extra path | Different vector identity | Ignored for repository README retrieval, but the submitted URL may imply a different revision or page |
| GitHub HTTP versus HTTPS | Different vector identity | Both schemes are accepted; fetched repository coordinate can be the same |
| YouTube alternate supported form | Different vector identity | Same extracted video ID |
| YouTube timestamp, playlist, or extra query | Different vector identity | Ignored by current video-ID extraction |
| YouTube unsupported form | Different or rejected identity | No extracted resource identity; cannot be equated |

No variant in the table is recommended as equivalent without a separately specified normalization and compatibility policy.

## 8. GitHub identity analysis

The effective remote-fetch identity is:

```text
owner/repository
```

with `.git` removed and only the first two path segments used.

The following are therefore the same fetch target under current code, but separate stored sources:

- `https://github.com/o/r`
- `https://github.com/o/r/`
- `https://github.com/o/r.git`
- `https://github.com/o/r/tree/main`
- `https://github.com/o/r?tab=readme`
- `https://github.com/o/r#readme`

Owner and repository strings retain their submitted case in API requests and metadata. Host matching lowercases `netloc`, but path-case equivalence is not established by the repository. Branch, ref, and path information beyond the repository coordinates do not change the repository README request, but they may change the resource the user intended.

A GitHub-specific logical identity could use the extracted owner/repository coordinate, potentially with an explicitly specified ref rule. That would be a new policy, not a clarification of existing storage behavior.

## 9. YouTube identity analysis

The effective remote-fetch identity is the extracted video ID.

The following are therefore the same fetch target under current code, but separate stored sources:

- `https://www.youtube.com/watch?v=ID`
- `https://www.youtube.com/watch?v=ID&t=30s`
- `https://www.youtube.com/watch?v=ID&list=PLAYLIST`
- `https://youtu.be/ID`
- `https://www.youtube.com/embed/ID`
- `https://www.youtube.com/shorts/ID`
- `https://www.youtube.com/live/ID`
- `https://www.youtube.com/v/ID`

Timestamp and playlist parameters do not change the current full-transcript retrieval behavior, but they can change user intent and navigation. Path and query casing are preserved in storage. The transcript response may normalize the returned video ID, but PAM does not promote that value to stored source identity.

Unsupported or unrecognized forms have no extracted identity and cannot be assigned to the same logical source merely because they appear related to a video.

A YouTube-specific logical identity could use the extracted video ID, but that would require explicit decisions about:

- Stored display URLs.
- Vector-source replacement.
- Removal semantics.
- Transcript-language or version differences.
- Unsupported forms.
- Historical rows.

## 10. D4 interaction

D4 Option A is locked:

- Lifecycle counters count recorded ingestion attempts.
- Multiple ledger rows may contribute to attempt counts.
- Historical rows remain evidence.

A cross-CWD duplicate URL ingestion may therefore legitimately increase attempt counts:

- First success: one `processed` row.
- Second success after a CWD change: another `processed` row.
- Failed retry: another `failed` row.

That accounting behavior must not be confused with logical-source identity. D4 permits multiple historical attempts; it does not authorize treating one remote resource as multiple logical sources for duplicate, removal, display, or retry-association purposes.

Likewise, fixing CWD-derived duplicate rows must not silently rewrite historical rows. Rewriting would alter the historical evidence on which D4 counting depends. Compatibility requires overlay matching, dual identity handling, migration, or another explicitly specified mechanism—not silent ledger mutation.

## 11. Desired invariants

### Invariant 1 — CWD independence

The same URL submitted from two working directories should not change its logical identity merely because the process CWD changed.

Current support:

- Supported for vector, graph, note, display, and removal-target identity through exact verbatim strings.
- Violated for ledger duplicate identity because `Path(url).resolve()` anchors the spelling to the CWD.

The existing vector architecture supports this invariant. The ledger conversion does not.

### Invariant 2 — Vector/ledger consistency

If two submissions represent the same logical remote source, vector and ledger identities should identify them consistently.

Current support:

- Supported for exact URL strings submitted from the same CWD.
- Unsupported across CWDs because of ledger mangling.
- Unsupported for URL variants because exact strings differ.

Achieving this invariant requires either verbatim/canonical ledger matching or a separate canonical identity used consistently by both storage layers.

### Invariant 3 — Failed retry consistency

A URL failure from CWD A should be recognizable as the same logical source when the same URL is retried from CWD B.

Current support:

- D3-B already permits the retry to proceed.
- The retry is not reliably associated with the earlier failed historical row.
- Failed-source display may show separate rows.
- D4 attempt counting will count both attempts.

Retrying is therefore permitted, but historical retry association is incomplete.

### Invariant 4 — Failed-source display consistency

Equivalent URL failures should be combinable only after a canonical identity exists.

Current `pam sources --failed` groups exact stored `original_path` values. It cannot safely combine:

- The same URL from different working directories.
- Semantically equivalent URL variants.

Combining them without a specified identity would risk merging distinct resources.

### Invariant 5 — Remove consistency

A failed-only URL should be removable regardless of CWD once a logical identity policy exists.

Current behavior:

- Removal from the original CWD can match the historical mangled ledger form.
- Removal from another CWD may fail to match that row.
- Removal of an indexed URL can still remove vector/graph data through the verbatim URL while leaving the historical row unmatched.

The desired invariant is not currently provided for failed-only URLs.

### Invariant 6 — Historical compatibility

A new identity policy must not silently make existing ledger entries unreachable.

Necessary compatibility analysis includes:

- Old CWD-derived successful rows.
- Old CWD-derived failed rows.
- Old `skipped_duplicate` rows.
- Multiple old rows for one URL.
- Existing verbatim vector rows.
- Repositories opened on another machine or path.
- Moved project roots.

## 12. Options A/B/C/D/E

### Option A — Exact submitted URL identity

Treat the exact URL string as the logical source identity.

Advantages:

- Simplest.
- Preserves current vector, graph, note, listing, and removal-display behavior.
- Avoids inventing semantic equivalence.
- Retains distinctions among tracking, signed, authenticated, revision-specific, and otherwise parameterized URLs.

Disadvantages:

- URL spelling variants remain separate sources.
- The demonstrated CWD defect remains unless ledger handling stops converting URLs with `Path.resolve()`.
- Cross-CWD behavior still needs an explicit verbatim-ledger or overlay-matching policy.
- Historical CWD-derived rows remain incompatible with exact matching unless a fallback is specified.

Compatibility:

- Fully compatible with existing vector and graph rows.
- Incompatible with historical CWD-derived ledger rows unless dual matching or migration is specified.

### Option B — URL-normalized identity

Normalize URLs with an explicit parser/canonicalizer before identity comparison or storage.

Potentially safe transformations, subject to a formal policy:

- Lowercase scheme and host for acceptance and comparison.
- Remove an explicitly default port only for the corresponding scheme.
- Preserve path and query casing.
- Preserve semantically meaningful query parameters.
- Do not merge authenticated, signed, revision-specific, or otherwise parameterized URLs without proof that the resource is unchanged.

Unsafe or context-dependent transformations:

- Stripping all query strings.
- Sorting or otherwise rewriting query parameters.
- Stripping fragments while treating the result as navigationally identical.
- Decoding percent-encoded characters without distinguishing reserved and unreserved characters.
- Normalizing dot segments using filesystem path semantics.
- Lowercasing paths.
- Removing trailing slashes universally.
- Following redirects and replacing the submitted identity with a transient destination.
- Removing user information or credentials from an identity while retaining access semantics.

Vector, ledger, graph, removal, display, and failed-source listing would all need to use the same normalized identity or a documented mapping. Historical rows would require dual matching or migration. This option carries the greatest normalization risk if applied generically.

### Option C — Ingestor-specific logical identity

Use the semantic identifier already extracted during ingestion:

- GitHub: owner/repository, with an explicitly specified branch/ref rule.
- YouTube: extracted and preferably response-confirmed video ID.

Advantages:

- Different spellings of the same remote resource can map to one logical source.
- Both ingestors already derive useful semantic identifiers.
- This is the only option that directly addresses URL-variant duplication as well as CWD dependence.

Problems:

- GitHub branch, ref, path, query, and case semantics need explicit rules.
- YouTube language, version, availability, unsupported forms, and response-confirmed IDs need explicit rules.
- Current `SourceDocument.source`, vector, graph, note, display, and removal behavior use submitted URLs.
- Changing stored identity could affect source display, removal compatibility, and knowledge ownership.
- Generic or future remote sources may not have an equivalent semantic identifier.
- Schema or migration implications may be substantial if the semantic identity is persisted separately.

This option best fits PAM’s adapter architecture, but it is a larger semantic change than a ledger-matching fix.

### Option D — Separate canonical identity from display URL

Retain:

```text
source/display_url
```

as the original submitted URL, and introduce a separate logical identity for:

- Duplicate detection.
- Ledger matching.
- Failed-source grouping.
- Removal.

Schema analysis:

- `ManifestEntry.from_dict` currently requires all existing fields and has no canonical-identity field.
- Adding a persisted canonical identity would require model, serialization, reader-tolerance, schema-version, and migration changes.
- An unpersisted runtime canonicalization could avoid schema changes but would still need historical-row compatibility.
- Existing `_source_forms`, `_canonical_source`, and `_manifest_entry_matches` already provide multi-form runtime matching, but they do not define a canonical URL identity.

Justification assessment:

- Justified only if URL variants or persistent historical compatibility require a stable identity distinct from display.
- Excessive if the only accepted goal is eliminating CWD dependence for exact duplicate URLs.
- Not appropriate for V1.1 without an explicit URL-equivalence policy.

### Option E — Narrow D3-C fix

Do not canonicalize semantically equivalent URLs. Eliminate only the demonstrated CWD dependency by using the verbatim URL, rather than `Path(url).resolve()`, for URL ledger matching and future URL ledger identity.

Effect analysis:

- Fixes cross-CWD duplicate detection for exact duplicate URLs.
- Preserves successful-path duplicate protection from the original CWD.
- Permits failed retries to remain associated with the same historical logical source.
- Allows future failed-source rows for the same spelling to group together.
- Allows future failed-only URL removal to work regardless of CWD.
- Preserves existing vector, graph, note, listing, and display identity.
- Does not merge URL variants.
- Does not require a universal URL canonicalizer.
- Historical CWD-derived rows remain incompatible with a verbatim-only lookup unless dual or fallback matching is specified.
- Dual matching preserves history without rewriting D4 attempt evidence.

Option E cures the demonstrated CWD defect without deciding URL-variant equivalence. It does not, by itself, supply a complete canonical-URL policy.

## 13. Backward-compatibility analysis

Existing ledger rows may contain forms such as:

```text
<old-CWD>/https:/github.com/o/r
```

or the corresponding project-relative mangled representation.

### 13.1 Existing successful URL row

A new verbatim or canonical identity will not match an old mangled row through exact comparison alone. Without compatibility handling, the same URL may be reprocessed and receive another successful row. Vector replacement remains idempotent for exact submitted URLs, but history gains another attempt.

### 13.2 Existing failed URL row

Without compatibility handling, a later exact duplicate may not be recognized as the same historical failure. D3-B still permits retry, but the failed-source display remains split and failed-only removal may remain directory-sensitive.

### 13.3 Existing `skipped_duplicate` URL row

The same compatibility limitation applies. A previous successful duplicate association may be lost for a new canonical identity unless old forms continue to match.

### 13.4 Multiple old CWD-derived rows

Multiple historical rows for one URL must be preserved as separate D4 attempts while being display-grouped only under an explicit canonical identity. They must not be merged, rewritten, or deleted as part of an identity fix.

### 13.5 Existing verbatim vector row

Existing vector rows are the most stable compatibility anchor because they do not embed filesystem working directories. A future URL policy can use exact vector identity for current indexed data while separately handling historical ledger spellings.

### 13.6 Repository opened from a new machine or path

A policy based on verbatim or semantic URL identity remains portable. A policy that embeds local filesystem prefixes does not. Old mangled rows transported with a repository cannot safely be interpreted through the new machine’s CWD.

### 13.7 Moved project root

A canonical URL identity should not depend on project-root location. Old rows that embed a former working directory or former project-relative derivation must be matched through historical-form compatibility, not current filesystem resolution.

### 13.8 Compatibility strategies

Possible mechanisms, without implementation:

- Exact old-form matching.
- Dual matching against both historical mangled and future canonical forms.
- Explicit fallback matching for rows lacking aCanonical identity.
- Lazy association without rewriting historical rows.
- Explicit migration with versioning and backup.
- Preservation of historical rows while using the new identity only prospectively.

Silent rewriting of `original_path` is incompatible with D4 historical-attempt semantics.

## 14. Remove behavior

### 14.1 Successful URL

`pam remove <verbatim-URL>`:

- Removes indexed vector chunks owned by the exact URL.
- Removes matching graph nodes and incident edges.
- Removes ledger rows matched through broad forms.
- May leave an older CWD-derived ledger row unmatched.
- Does not rewrite vector identity.

### 14.2 Failed-only URL

`pam remove <verbatim-URL>`:

- Has no vector or graph anchor.
- Can match a historical ledger row created under the current CWD.
- May report “Source not found” for the same URL when the only historical row was created under another CWD.
- The row remains visible to `pam sources --failed` even though removal cannot address it under the current directory.

### 14.3 URL created under another CWD

The submitted verbatim URL reliably identifies indexed vector/graph data. It does not reliably identify the historical ledger spelling. Removal may therefore be partial: indexed data is removed while historical ledger evidence remains.

### 14.4 URL variant

A variant is a separate vector identity and normally a separate ledger identity. Removing one variant does not remove another merely because both retrieve the same remote content. A bare filename shared by URL variants may trigger ambiguity protection rather than deletion.

### 14.5 Multiple equivalent URL ledger rows

Current removal has no canonical equivalence grouping. Each row must match the supplied forms independently. A canonical identity policy would need to decide whether one removal operation should delete all historical attempt rows associated with that logical source or only rows matching the supplied spelling. D4 attempt-count semantics make silent deletion or consolidation consequential and therefore require explicit specification.

A narrow fix can preserve existing remove behavior by adding canonical matching as an additional matching path rather than replacing exact-form matching.

## 15. Security and correctness considerations

URL normalization can create false identity collisions. A future policy must not equate URLs merely because they appear similar.

### 15.1 Query parameters

Query strings may:

- Select a different video.
- Select a playlist or timestamp context.
- Carry tracking parameters.
- Carry authentication or signature material.
- Change server behavior.

GitHub repository-coordinate extraction currently ignores queries, while YouTube extraction treats `v` as semantically essential. A universal query-stripping rule is unsafe.

### 15.2 Fragments

Fragments may:

- Identify a document section.
- Change navigation without changing the retrieved document.
- Distinguish user intent while leaving server content unchanged.

Treating all fragment variants as the same logical source may be acceptable for duplicate-content purposes but unsafe as a universal display, citation, or removal policy.

### 15.3 Path case

Current storage preserves path casing. YouTube and GitHub extraction preserve owner, repository, path, and query casing even while lowercasing hosts for acceptance. Changing path case could merge distinct resources or alter repository/video identifiers. No case-folding rule should be adopted without ingestor-specific proof.

### 15.4 Percent encoding

Unreserved-character decoding may be syntactically safe in isolation, but PAM has no parser and no policy distinguishing:

- Reserved characters.
- Unreserved characters.
- Encoded delimiters.
- Encoded authentication material.
- Encoded path traversal sequences.

Percent normalization must not be introduced as a side effect of a CWD fix.

### 15.5 Redirects

A submitted URL and a redirect destination are not necessarily the same logical source over time. Redirects can change, expire, or depend on authentication, geography, A/B behavior, or repository moves. PAM should not replace user-submitted identity with a transient fetch destination without an explicit policy.

### 15.6 Authentication-bearing URLs

`urlparse(...).netloc` can include user information. Normalization must not:

- Drop credentials while preserving privileged access semantics.
- Merge authenticated and unauthenticated forms.
- Merge different credential scopes.
- Log or persist secrets more broadly than necessary.

The current code has no URL-credential redaction path. Any identity policy that accepts authenticated URLs must separately specify storage, logging, display, matching, and removal constraints.

### 15.7 Signed URLs

Expiring or capability-bearing signed URLs must remain distinct unless expiration, scope, and resource equivalence are explicitly modeled. Collapsing them could grant an old signed reference the identity of a current one or vice versa.

### 15.8 GitHub branch and reference paths

The current GitHub fetcher ignores path segments after owner and repository. Treating all such URLs as identical for storage would discard user-supplied revision or path context. That may be acceptable for repository-README duplicate handling, but it is a semantic decision, not a safe syntactic normalization.

### 15.9 YouTube query parameters

The `v` parameter identifies the video under current extraction. Other parameters may affect context without changing the transcript fetched by PAM. They nevertheless distinguish user intent and potentially signed or contextual access. They should not be stripped universally.

### 15.10 Correctness principle

“Syntactically equivalent” and “semantically equivalent for this ingestor” are different standards. Only the latter can justify shared ingestion identity, and the latter must be established separately for GitHub, YouTube, and any future remote adapter.

## 18. Exact unresolved decisions

A complete URL-identity policy requires decisions on:

1. Whether exact duplicate URLs across working directories are the same logical source.
2. Whether semantically equivalent URL spellings are the same logical source.
3. Whether URL identity applies only to ledger matching or across vector, graph, note, listing, display, and removal layers.
4. How `SourceDocument.source` should represent a canonical remote source, if at all.
5. Whether equivalent URL variants should share vector chunks and generated notes.
6. How canonical URL identity interacts with branch, ref, path, query, fragment, encoding, authentication, signature, and redirect semantics.
7. Whether historical CWD-derived URL rows receive dual matching, lazy association, explicit migration, or prospective-only handling.
8. How failed-only URLs are removed across directories.
9. How equivalent URL failures are grouped without merging distinct resources.
10. Whether a canonical identity is persisted, derived at runtime, or both.
11. Whether the change is limited to exact URLs or includes ingestor-specific semantic identifiers.

## 19. Recommended policy

The repository evidence supports a partial, but not complete, URL-identity conclusion.

Supported by existing architecture and specifications:

- The same verbatim URL submitted from different working directories should be the same logical source.
- Exact submitted URLs should remain the operational vector, graph, note, listing, and display identity unless a broader equivalence policy is explicitly adopted.
- Ledger duplicate handling should not derive a different identity for the same verbatim URL merely because the process working directory changed.

Not supported by existing evidence:

- Treating trailing-slash, query, fragment, encoding, host-casing, branch, ref, playlist, timestamp, authentication, signed, or redirected variants as identical.
- Changing stored vector or display URLs to semantic identifiers.
- Adding a persisted canonical-identity schema field.
- Silently rewriting or merging historical CWD-derived ledger rows.

Accordingly:

```text
Specification decision required.
```

The evidence justifies Option E as the narrow evidence-compatible direction for the demonstrated CWD defect, but it does not justify selecting a complete canonical-URL policy. Variant equivalence, compatibility handling, persistence, removal scope, and display identity remain undecided.
