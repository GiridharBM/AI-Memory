# V1.1.0 D3-C — Path / CWD Normalization Audit

**Status:** AUDIT ONLY — no implementation performed.
**Date:** 2026-09-30.
**HEAD:** `b7f8ae236dffc9743083cb0c42d03c7890dd0927`.
**Scope:** Determine the intended identity for local filesystem sources, URL sources, and repeated invocations from different working directories.

---

## 1. Executive summary

D3-C is not a single defect. The evidence supports three different classifications:

1. **Local filesystem paths: specification gap and narrow design limitation, not an actual production defect in the normal CLI/GUI/queue paths.**
   - Upstream code normally converts a local file to an absolute, resolved filesystem identity before ledger, vector-store, and duplicate-detection operations.
   - `ManifestManager._normalize_path` remains CWD-sensitive when it is directly given a raw relative path, but no tested production ingestion, retry, removal, or listing path was found to depend on that residual behavior for ordinary local files.

2. **URL ledger identity: narrow, observable lifecycle defect.**
   - A URL string is not an absolute `Path`.
   - Consequently, `Path(url).resolve()` anchors the URL-derived ledger identity to the process’s current working directory.
   - The same URL, same ledger file, and same project root can therefore produce different `original_path` values and different duplicate/skip outcomes when the commands are run from different directories.

3. **Broad matching in removal and source annotation: intentional resilience, with a known URL/CWD boundary.**
   - `pam remove` and source annotation deliberately consider absolute, project-relative, filename, verbatim-URL, and mangled-URL forms.
   - This resilience substantially limits the user impact of identity-spelling differences, but it does not fully solve failed-only URL rows created under different working directories.

Accordingly, D3-C should remain open only as:

- a narrow URL-identity and public-path-helper contract item, not
- a broad local-filesystem normalization redesign.

No implementation, test, configuration, documentation, commit, staging, or push was performed except for creating this audit report.

## 3. Source identity model

The repository uses complementary, subsystem-specific identities rather than one universal canonical string:

| Subsystem | Local filesystem identity | Remote URL identity |
|---|---|---|
| Ingestion service and `SourceDocument.source` | Absolute resolved path | Submitted URL verbatim |
| Vector store and knowledge graph | Absolute resolved path | Submitted URL verbatim |
| Generated-note front matter | Absolute resolved path | Submitted URL verbatim |
| Manifest `original_path` | Project-relative representation of an absolute resolved path, where possible | CWD-derived `Path`-mangled representation |
| Manifest `sha256` | Content hash for supported extensions | Empty for URL/non-hashable sources |
| Removal and source annotation | Multiple absolute, relative, resolved, verbatim, and mangled forms | Multiple verbatim and mangled forms |
| Queue in-memory identity | Resolved filesystem path | Queue does not ingest remote URLs |

The distinction between a persisted display/storage spelling and the operational identity is important:

- For an absolute local file, the manifest may store a project-relative string, but it is derived from the absolute resolved path.
- For a URL, the manifest stores a CWD-dependent mangled path even though the operational vector identity is verbatim.

## 4. `_normalize_path` analysis

`app/infrastructure/state/manifest.py:231-239`:

```python
candidate = Path(path)
try:
    return str(candidate.resolve().relative_to(self.project_root))
except ValueError:
    return str(candidate.resolve())
```

Behavior:

1. Accepts `None` and returns an empty string.
2. Calls `Path.resolve()` on the supplied value.
3. Converts the resolved value to a project-relative string when possible.
4. Otherwise stores the resolved absolute string.

CWD dependence:

- If the supplied path is absolute, `resolve()` does not use the process CWD to select the target.
- If the supplied path is relative, `resolve()` anchors it to the process CWD.
- `project_root` itself is application configuration and is not derived from the invocation CWD.
- The existing project-root-relative conversion is deterministic only after resolution; it does not first anchor a relative input to `project_root`.

Therefore:

- `_normalize_path` is **CWD-independent for absolute inputs**.
- `_normalize_path` is **CWD-sensitive for raw relative inputs**.
- URL strings are non-absolute `Path` values, so their ledger representation is also **CWD-sensitive**.

The prior D3 observation that `_normalize_path` is CWD-dependent is accurate as a statement about the helper in isolation, but it does not establish that ordinary local-file production flows submit relative paths to it.

## 5. `_source_forms` analysis

`app/cli/entry.py:1537-1576` builds candidate identities for a removal target.

For a non-URL filesystem value:

- Absolute inputs are resolved without CWD dependence.
- Relative inputs are explicitly joined to `project_root` before resolution.
- The function includes absolute, resolved, project-relative, and lexical relative forms.

The associated comment explicitly states that relative inputs are resolved against the project root so removal works from any directory.

For a value containing `"://"`:

- The function includes the verbatim string.
- It also calls `Path(source).resolve()`.
- An isolated `pathlib` check confirmed that `Path("https://github.com/example/pam").is_absolute()` is false and that resolution produces different absolute strings under different working directories:
  - `<CWD-A>/https:/github.com/example/pam`
  - `<CWD-B>/https:/github.com/example/pam`

Accordingly, the prior broad claim that `_source_forms` is CWD-independent needs correction:

- Filesystem spellings: CWD-independent.
- URL spellings: CWD-sensitive for the derived mangled forms.
- Verbatim URLs remain independent of CWD because they are copied unchanged into the candidate set.

## 6. `_canonical_source` analysis

`app/cli/entry.py:1579-1592`:

```python
p = Path(value)
if not p.is_absolute():
    p = project_root / p
try:
    return str(p.resolve().relative_to(project_root))
except ValueError:
    return str(p.resolve())
```

Unlike `_normalize_path`, this helper anchors every non-absolute input to `project_root` before resolution. Its output is therefore independent of the process CWD, although it remains dependent on the configured `project_root`.

For a verbatim URL, it produces a project-root-anchored mangled path. That output is stable across working directories but is still not a semantic URL canonical form: equivalent URLs with trailing slashes, query strings, different host casing, or different URL spellings remain distinct.

`_manifest_entry_matches`, at lines 1595-1613, combines:

- Exact `original_path` equality.
- Exact `original_filename` equality.
- Resolution of the stored `original_path` against the current CWD.
- Basename comparison.

The last operation reintroduces CWD dependence into an otherwise broad matching process.

## 7. Duplicate-detection behavior

### Hashable local sources

`contains_successful_hash` compares only content digests:

```python
entry.sha256 == sha256 and is_successful_status(entry.status)
```

at `app/infrastructure/state/manifest.py:100-102`.

Consequences:

- The same file contents produce the same digest regardless of absolute/relative invocation spelling.
- Duplicate detection is independent of process CWD.
- Ledger storage may still record different-looking rows for different spellings, but repeated ingestion is duplicate-protected by content.
- A moved or renamed file with unchanged contents remains a hash duplicate, even though its path identity differs.

### Non-hashable or undigestible filesystem sources

When `digest is None`, both CLI and GUI ingestion use:

```python
manifest.contains_successful_path(ledger_path)
```

at `app/cli/entry.py:1093` and `app/interfaces/web/routes/interact.py:276`.

Ordinary local non-hashable flows supply absolute filesystem paths:

- CLI typed arguments declare `resolve_path=True`.
- GUI uploads return an absolute configured staging path.
- Queue paths are resolved before in-memory duplicate handling.

Those absolute paths normalize to the same project-relative ledger form when the configured project root is unchanged. No residual CWD dependence was found for ordinary absolute local-file flows.

A residual CWD effect remains for:

- Direct calls to `_run_ingest` with a raw relative string or `Path`.
- Direct ledger calls using project-relative or otherwise unresolved paths.
- Tests or integrations that bypass CLI argument resolution.
- URL strings, discussed separately below.

No production test or code path was found exercising a raw relative filesystem path through ingestion duplicate detection while changing CWD.

### Remote URLs

A URL always takes the digest-free path:

```python
digest = manifest.hash_for_path(source) if isinstance(source, Path) else None
```

at both `app/cli/entry.py:1070` and `app/interfaces/web/routes/interact.py:256`.

The duplicate decision then depends on:

```python
manifest.contains_successful_path(Path(url))
```

Because `Path(url)` is non-absolute, the normalized identity differs by process CWD.

Observable consequences include:

- The same URL may be classified as `skipped_duplicate` when resubmitted from the original CWD.
- It may instead run the ingestion workflow when resubmitted from another CWD.
- Successful re-ingestion remains vector-idempotent because the vector operation uses the verbatim URL.
- The ledger may gain another `processed` row rather than a `skipped_duplicate` row.
- A prior success therefore does not reliably protect the same URL against reprocessing across CWDs.

This is an actual, code-traceable lifecycle difference, not merely a theoretical spelling difference.

## 8. Remove behavior

`pam remove`, at `app/cli/entry.py:468-597`:

1. Expands the user-supplied source with `_source_forms`.
2. Loads vector, knowledge-graph, and ledger state.
3. Calculates canonical source identities.
4. Aborts when more than one distinct source matches.
5. Aborts when no source matches.
6. Adds resolved absolute forms so vector, graph, and ledger ownership keys agree.
7. Removes vector and graph entries by resolved source.
8. Removes matching ledger entries by pre-resolved absolute path.

This breadth is intentional. A4 explicitly:

- Anchored relative removal inputs to `project_root` rather than CWD.
- Uses exact path identity for ledger rows.
- Treats ambiguous basename matches as abort conditions rather than silently selecting one source.
- Supports verbatim and mangled URL forms.

Relevant evidence appears in `docs/phases/59_PHASE_V1_1_A4_PAM_REMOVE_HARDENING.md:41-59` and `...:81-88`.

Why removal is more resilient than ingestion duplicate detection:

- Removal consults multiple independent identity forms.
- It can match a source through vector identity even when the ledger spelling differs.
- Duplicate ingestion makes an immediate equality or successful-status decision without that broader fallback.
- URL removal still works reliably when the submitted verbatim URL corresponds to indexed vector or graph sources.

A remaining URL boundary is:

- Failed-only URL sources have no vector or graph identity.
- Removal from a different CWD can fail to match a historical CWD-derived ledger row.
- The result is a truthful “Source not found,” but the user can still see the row in `pam sources --failed`.

There is no GUI removal endpoint. The API exposes source listing and detail through `/sources` and `/sources/{identifier}`, but no corresponding removal route was found. GUI removal behavior is therefore the CLI-only path.

## 9. CLI versus GUI behavior

### Filesystem file ingestion

| Stage | CLI | GUI |
|---|---|---|
| User-supplied value | Filesystem path argument | Uploaded filename |
| Pre-ingestion identity | Declared `resolve_path=True` | Absolute configured staging path |
| Workflow input | Resolved original file | Staged copy |
| `document.source` | Absolute resolved original path | Absolute resolved staged path |
| Ledger identity | Absolute resolved original path, then project-relative storage | Absolute resolved staged path, then project-relative storage |
| Hash duplicate handling | Content-based | Content-based |
| Path duplicate handling | Successful path entries | Successful path entries |

For hashable files, CLI and GUI agree on the duplicate outcome even though they do not generally ingest the same physical file object: GUI stages a copy. If either submission has already been processed successfully, hash equality causes a duplicate skip before vector replacement.

For non-hashable files, the two paths are not interchangeable identities:

- CLI records the original absolute filesystem path.
- GUI records the staged copy’s absolute path.
- Both are CWD-independent as absolute paths, but they identify different filesystem objects.

### URL ingestion

CLI and GUI use the same submitted string, workflow, duplicate helper, and append-only ledger behavior. They therefore share the same CWD-dependent ledger-identity limitation. No CLI/GUI divergence was found for URL duplicate logic.

### Removal and listing

- `pam remove` is CLI-only.
- `/api/sources` uses the same CLI row construction and ledger-annotation helpers.
- GUI source display consequently inherits CLI annotation semantics.
- `pam sources --failed` groups the stored `original_path` without cross-CWD normalization, so duplicate URL ledger forms can appear as separate failed-source rows.

## 10. Hashable-source analysis

Hashable behavior is effectively immune to CWD for duplicate and retry decisions.

Supporting facts:

- Supported extensions are enumerated in `app/infrastructure/state/hashing.py:15-18`.
- `compute_file_hash` operates on file bytes, not path spelling.
- CLI, GUI, and queue all use content digests before path-only duplicate logic.
- D3 retry preserves hashable retry behavior and excludes unsuccessful hashes.

Theoretical differences, such as different ledger-display spellings for the same bytes, do not produce observable duplicate/retry differences in the tested production flows. They may affect D4 attempt tallies because D4 intentionally counts ledger rows rather than distinct sources, but that is approved Option A behavior, not a D3-C defect.

## 11. Non-hashable-source analysis

Local non-hashable or unsupported sources have an observable lifecycle only through path identity because no digest is available.

Current ordinary behavior:

- `pam ingest file` supplies an absolute filesystem path after CLI resolution.
- GUI supplies an absolute staging path.
- Both normalize to the same stored form when they address the same absolute target and project root.
- `contains_successful_path` then provides successful-path duplicate protection.
- D3-B permits retries after failed entries while preserving duplicate protection for successful entries.

The residual CWD issue is limited to:

- Raw relative strings or `Path` objects supplied directly to lower-level ingestion or ledger APIs.
- URLs, addressed separately.

No code or test evidence was found that ordinary CLI, GUI, or queue non-hashable local-file operations receive relative paths at the duplicate-decision point. Accordingly, local non-hashable CWD dependence is a **design limitation and API-contract gap**, not an established user-facing defect.

## 12. URL identity analysis

### Stored identities

For one GitHub URL, the subsystems record different strings:

- Ingestion service: verbatim URL.
- `SourceDocument.source`: verbatim URL.
- Vector and graph sources: verbatim URL.
- Ledger `original_path`: CWD-derived `Path`-mangled path.
- Ledger `original_filename`: `Path(url).name`.

The existing test helper in `tests/unit/test_cli_remove.py:138-146` documents this split directly:

- Vector and graph key by verbatim URL.
- Ledger uses the project-relative mangled form.
- The ledger row is written directly in tests to avoid CWD/drive artifacts.

### CWD behavior

Because `Path(url)` is non-absolute:

- The same URL produces different ledger identities from different working directories.
- The same URL can therefore bypass `contains_successful_path` after a directory change.
- It can also produce multiple failed-source display rows under `pam sources --failed`.
- Existing D3 tests invoke URL ingestion twice in the same process/CWD, so they do not cover cross-CWD behavior.

### Semantically equivalent URLs

No URL canonicalizer was found. The code preserves the supplied string throughout ingestion, vector storage, graph storage, and display. Consequently, variants that identify the same remote resource—such as trailing slashes, query strings, letter-case differences where applicable, shortened URLs, and repository URLs with different path suffixes—are distinct ingestion identities.

GitHub and YouTube ingestors parse semantic resource identifiers internally:

- `app/infrastructure/ingestion/github_readme_ingestor.py:43` parses repository coordinates.
- `app/infrastructure/ingestion/youtube_transcript_ingestor.py:46` extracts a video ID.

Those identifiers are used to fetch remote content, but they are not used as the stored `SourceDocument.source`. Thus equivalent URL spellings can create separate vector sources and ledger rows.

### Classification

URL identity is:

- **A:** part of the same D3-C canonical-identity problem, because both filesystem-relative and URL ledger identities depend on process CWD through `Path.resolve()`.
- **B:** operationally separate, because filesystem remediation based on absolute paths cannot apply to remote URLs and because verbatim URL storage is independently documented.
- **Not C:** not fully intentional. Verbatim vector identity is intentional, but the CWD-dependent ledger consequence is a known limitation rather than a specified behavior.

A4’s known-limitation section already flags URL ledger normalization under different drives at `docs/phases/59_PHASE_V1_1_A4_PAM_REMOVE_HARDENING.md:165-169`. Cross-CWD URL behavior is the same class of unresolved identity limitation.

## 14. Backward-compatibility analysis

### Existing stored forms

Changing interpretation of `./docs/file.md` to a consistently project-root-anchored `D:\Projects\...\docs\file.md` would interact with at least three historical categories:

1. Absolute local inputs already represented as project-relative ledger rows.
2. Relative or API-supplied inputs interpreted under a prior process CWD.
3. CWD-derived URL rows.

### Likely consequences of an incompatible change

| Change | Duplicate ingestion | Missed prior ingestion | Remove mismatch | Source-list duplication | Failed-retry mismatch |
|---|---|---|---|---|---|
| Anchor raw relative ledger inputs to `project_root` | Possible for rows created under a different CWD | Possible for old CWD-derived rows | Possible for old rows outside the new interpretation | Possible if old and new display spellings diverge | Possible for old non-hashable rows |
| Leave absolute-input behavior unchanged | No | No | No | No | No |
| Normalize URL strings to a canonical remote identifier without migration | Possible until old rows migrate | Possible for old mangled rows | Possible for failed-only URL rows | Possible for `--failed` listings | Possible because old failed rows would not match the new identity |
| Change vector `source` from absolute to project-relative | Yes; exact-match removal and listing would diverge | Yes | Yes | Yes | Secondary effect through source matching |
| Move or rename the configured project root | Possible for non-hashable sources | Possible for ledger/path identities | Possible | Possible | Possible |

### Compatibility notes

- Existing absolute local-file flows are the least sensitive: absolute paths already normalize through the installed project root and retain hash protection where available.
- Existing relative ledger rows are most sensitive because their original CWD cannot be recovered from the stored string alone.
- Existing CWD-derived URL rows are sensitive because the URL itself contains no record of the creating process’s working directory.
- Changing only the vector-store representation would be more dangerous than changing only ledger-input interpretation, because vector removal and indexed-source grouping depend on exact `source` equality.
- D4 Option A tolerates multiple attempt rows, but it does not resolve whether two rows represent one logical source. A compatibility migration would therefore need either dual-form matching or an explicit ledger-migration policy.

No migration or modification was performed.

## 17. Options A/B/C/D

### Option A — Preserve current behavior

Document that ledger identity may depend on invocation CWD where hash identity is unavailable.

This option would need to distinguish:

- Ordinary absolute local-file operations, which are already CWD-independent.
- Raw relative ledger inputs, which remain CWD-sensitive.
- URL ledger entries, which remain CWD-sensitive.
- Content-hash duplicates, which remain independent of path spelling.

The existing A4 URL/drive limitation and the remove-test seeding workaround would become part of the permanent specification if Option A were selected. No repository evidence was found expressly selecting permanent CWD-dependent URL duplication as intended behavior.

### Option B — Canonical absolute-path identity

Normalize local filesystem sources to a canonical absolute path independent of CWD.

Evidence already supports this direction for local files:

- Ingestion-service documents use absolute resolved paths.
- Vector and graph sources use absolute resolved paths.
- CLI filesystem arguments declare path resolution.
- Removal anchors relative inputs to project root.
- Configuration anchors relative state paths to project root.

Implications:

- Existing absolute-input ledger rows would generally be unaffected.
- Raw relative-input rows created under another CWD could become unreachable.
- Project-root moves would still change the derived project-relative storage form.
- Vector-store identity should remain absolute rather than being converted to project-relative storage.
- URL sources cannot be addressed by filesystem absolute-path canonicalization and require separate treatment.

### Option C — Canonical identity layer

Introduce a dedicated source-identity representation separate from display and original-path storage.

Potential shape:

- Hashable files: content digest plus canonical absolute path.
- Non-hashable files: canonical absolute path and project-root context.
- URLs: normalized remote-resource identifier plus preserved display string.

Justification assessment:

- The repository already has substantial matching machinery in `_source_forms`, `_manifest_entry_matches`, and `_canonical_source`.
- A new identity field or schema would affect ledger compatibility and likely require migration.
- For local files, the existing absolute upstream normalization makes a new layer disproportionate to the demonstrated defect.
- For URLs, a focused canonicalization approach would be narrower than a general identity-layer redesign.
- Option C is therefore excessive for V1.1 unless URL canonical identity is explicitly required.

### Option D — Separate URL identity treatment

Treat genuinely distinct URL behavior separately from filesystem normalization.

This option recognizes that:

- Absolute-path normalization solves relative-path ambiguity but not URL identity.
- Verbatim URL preservation is independently specified for ingestion, vector, graph, and display behavior.
- Ledger duplicate detection and failed-source grouping need a stable remote identity.
- Equivalent URL spellings also need a canonicalization rule if duplicate URL ingestion is to be prevented.
- D3-C filesystem conclusions should not dictate URL semantics.

No option is selected by this audit.

## 18. Whether D3-C is an actual defect

D3-C is **partly an actual defect, partly a specification gap, and partly intentional behavior**.

### Actual defect: URL ledger identity

The same URL, ledger file, project root, and ingestion policy can produce different identities and duplicate outcomes solely because the process working directory differs. This is observable, code-traceable, and user-visible in duplicate ingestion, ledger history, failed-source display, and failed-only URL removal.

It is a narrow defect in URL ledger identity, not a defect in:

- URL fetching;
- verbatim vector storage;
- successful vector replacement;
- failed-entry preservation;
- D4 attempt counting;
- hashable duplicate protection.

### Specification gap/design limitation: raw local relative paths

`ManifestManager._normalize_path` has no documented contract for raw relative paths. Its CWD-dependent `Path.resolve()` behavior is a latent API limitation. No tested production flow was found that exposes it for ordinary local files because CLI, GUI, queue, and ingestion normalization supply absolute paths.

### Intentional behavior: broad removal and source annotation

Extensive multi-form matching is documented, implemented, and tested for `pam remove` and source annotation. Its URL/CWD boundary is incomplete, but the breadth itself is deliberate rather than accidental.

## 19. Whether a specification decision is required

A decision is required only for the narrow unresolved portion:

1. What constitutes a canonical URL identity for ledger duplicate detection, failed-source grouping, and failed-only URL removal?
2. Whether semantically equivalent URL spellings should be treated as the same ingestion source.
3. What contract `_normalize_path` guarantees when directly supplied a raw relative path.

No specification decision is required to establish the ordinary local-file model. Existing documentation already identifies absolute resolved paths as the local operational identity and project-relative ledger strings as a derived representation.

No implementation is warranted by this audit.
