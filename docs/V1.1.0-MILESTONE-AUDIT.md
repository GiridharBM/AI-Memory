## A. Overall Result

**⚠ STATUS: `gaps_found`** — the V1.1.0 acceptance matrix passed when written, and the milestone's headline scope shipped. However, re-verification against the current tree found **three data-integrity defects on read paths** and **one unclosed lifecycle leg**. None of these block the already-published release tag, but they are real and two of them can destroy durable user state.

The V1.1.0 *scope* is delivered; the V1.1.0 *definition of done* ("truthful, read-only, non-destructive lifecycle over one durable ledger") is **not fully met**.

## D. Critical gaps

### D.1 `pam remove` silently wipes a corrupt vector store (data loss)
- **Severity: HIGH.** `VectorStore._load` returns an empty store on parse error (`vector_store.py:179–183`, logs a warning only). `pam remove` then removes 0 entries and calls `store.save()` unconditionally (`entry.py:490–491`), overwriting the file with `{"entries": []}`.
- **Impact:** all 31 sources' vectors are destroyed by a single `pam remove` against a corrupt store. A4 hardened the *KG* corrupt path (`entry.py:411–423`, "nothing was removed", exit 1) but not the vector store.
- **Verdict:** contradicts criterion 7 and 13.

### D.2 `pam sources` quarantines and rewrites a corrupt ledger (data loss)
- **Severity: HIGH.** `pam sources` constructs `ManifestManager` (`entry.py:276–281`); `__init__`→`load()` does `mkdir` + `save()`, and on a corrupt manifest quarantines the original to `processed_files.corrupted.json` and writes a fresh empty one (`manifest.py:47–52, 59–65`).
- **Contrast:** A5 explicitly documents this hazard and uses the read-only reader (`entry.py:1219–1222`). A1 was never migrated.
- **Verdict:** a "read" command destroys durable ledger state; contradicts criterion 10 and A1's own "read-only" claim (`61:196`).

### D.3 Failed-only sources are invisible → the "view → retry" leg is unclosed
- **Severity: MEDIUM.** A1 rows come exclusively from the vector store (`entry.py:313–343`); a source that fails before indexing has no vectors. A2's retryable-failure panel (`entry.py:1170–1177`) therefore has no read-side counterpart. AC7 (`pam sources --failed`) was deferred and remains undelivered.
- **Consequence:** the milestone lifecycle is closed for ingested sources, open for failed ones.

### D.4 Retried-source count semantics — CLOSED (Option A)
- **Status: CLOSED.** D4 selects Option A: lifecycle ingestion counters intentionally represent recorded ingestion attempts in the durable ledger, not distinct logical sources in their current state. A source with separate failed and processed attempts therefore contributes once to `Failed` and once to `Successful ingests`.
- `entry.py:448–452` lets `failed` unconditionally win over later successful entries; the ledger is append-only with no supersession. That behavior is retained as historical attempt evidence, not as a claim that the source is currently broken.
- **Live proof:** a PDF with `failed@12:05Z` then `processed@16:39Z` that *is* in the vector store still shows `failed`. Under D4, that means one recorded attempt failed at `12:05Z` and another succeeded at `16:39Z`.
- **Consequence:** the former “false-negative” framing is superseded. Current indexed-source state remains represented separately by vector-store source counts and per-source status views. The locked per-source precedence—`failed > processed > skipped_duplicate > indexed`—is unchanged.

## H. Recommendation

V1.1.0 shipped and its published acceptance matrix stands as written. These findings are **post-release integrity gaps**, not reasons to retract the tag. Recommended as a follow-up (ordered by blast radius):

1. **D.1** — make `pam remove` refuse to run (exit 1, "nothing removed") when the vector store fails to load, mirroring A4's existing corrupt-KG guard at `entry.py:411–423`.
2. **D.2** — migrate `pam sources` (and the GUI `knowledge.py`) to `_read_manifest_entries` (`entry.py:1216`) so all read paths share A5's non-mutating contract.
3. **D.3** — either deliver `pam sources --failed` or add an explicit "unlisted failed sources" line so the retry leg is visible.
4. **D.4 — CLOSED.** Option A was selected. Lifecycle ingestion counters intentionally represent recorded attempts/ledger entries; retain the existing `failed`-wins precedence and append-only ledger. No implementation change is required.

None of these touch the frozen retrieval pipeline. None require a version bump.
